# 官方数据 ZIP 完整性核查与四天计划调整

核查日期：2026-10-29，北京时间。本次只读取数据并生成检查报告，没有训练模型、改动原 ZIP 或修改原 Harness 的数据准入状态。

## 结论

**从任务覆盖、文件完整性、标签可读性以及与官方提交模板的逐行对应关系看，这份 ZIP 的数据主体齐全，足以开始真实数据接入与基线开发。** 22 个任务均有 train、valid、test，未发现缺任务、缺文件或压缩损坏。测试数据与已核验的官方模板全部对应。

**说明材料并不齐全。** ZIP 只有 CSV，没有 README、标签单位/正类语义/变换说明、额外数据字典、3D 坐标或预计算特征。没有这些文件不等于训练数据损坏；官方任务允许 SMILES 输入，可先按实际提供的数值标签开发。仍需区分“能读出官方 Y”与“已确认其完整生物学解释”，不要根据经验额外对标签取对数或改阈值。

前面的评审有两项假设已被本次证据解除：**训练包尚未取得**、**可能只有单个标注文件需要我们自行划分**。四天计划可以更早进入真实运行，原定“派生划分接口”应从首日必做工作中移除。

## 实际发现的易错点

### 1. 官方划分已提供，第一版直接使用

22 个任务中，每个任务自己的 train/valid/test 两两均没有完全相同的 SMILES 字符串交叉。此项没有证明不同字符串一定代表不同分子，也未验证骨架分离。

不需要为了满足原 Harness 而重新切数据。将官方 `valid.csv` 登记为执行器的 `validation` 角色即可；每个任务的 train/valid/test 保持来源与行顺序。是否追加独立研究划分可以后移，不替换现有官方划分。

### 2. 不能按药物 ID 或 SMILES 直接去重、覆盖记录

hERG 的 train 有 20 行空 Drug_ID，valid 有 1 行，test 有 1 行。测试空 ID 与官方模板一致。ID 缺失并不表示 SMILES 或标签缺失，样本身份应保留任务、划分和原始行号。

以下任务的 train+valid 中，同一原始 SMILES 存在不同数值标签：

| 任务 | 对应不同数值标签的 SMILES 组数 |
|---|---:|
| bbb_martins | 8 |
| caco2_wang | 3 |
| clearance_hepatocyte_az | 153 |
| half_life_obach | 1 |
| ld50_zhu | 20 |
| ppbr_az | 551 |
| vdss_lombardo | 12 |

例如 bbb_martins 的 train 原始行 1、3 是相同 SMILES，标签分别为 1、0；ppbr_az 存在同一分子的多次不同测量。这不证明文件损坏，可能涉及实验重复或源数据差异。本轮没有擅自纠正或聚合标签。

第一版保留原始记录及划分，禁止用 `dict[smiles] = label` 之类操作静默丢掉此前记录。B 决定是否需要训练内的聚合策略并记录依据；任何处理不能改变测试模板的行覆盖。

### 3. 多任务合表必须保留每个任务自己的划分

观察到 5,589/11,735 条验证记录（约 47.6%）、9,148/16,379 条测试记录（约 55.9%）的 SMILES，也出现在其他任务的 train 中。它们是其他终点的训练记录，并非已发现同一终点的验证/测试标签泄漏，也不是外部数据。

这会影响多任务模型的数据组织：同一个分子在任务 A 是 train，在任务 B 可能是 valid。不能先混合所有 train/valid 标签形成一张分子表，再把已混入验证标签的表整体拿去拟合。

初版建议按 `(task, split, row_index)` 保留监督记录；共享分子编码时，对每个任务的损失严格使用该任务允许的训练标签，验证标签只作验证。若为了科学比较追加按分子分组的检查，应明确它与官方提供划分的不同，不能把额外切分擅自当官方要求。

### 4. 数据规模与标签噪声差异较大

每任务训练行数从 dili 的 331 到 cyp2d6_veith 的 9,191，相差约 28 倍。验证集最少仅 48 行；cyp2c9_substrate 的验证集只有 12 个正例，hia_hou 的验证集只有 10 个负例。少量预测变化就可能影响指标，应避免依据一次微小变化频繁换模型。

回归值域也不同，例如 caco2_wang 验证标签为负数，half_life_obach 验证范围 0.37–820。实际单位和是否已有对数变换未在 ZIP 说明，不能对所有任务使用同一经验变换。简单基线可以学习官方提供的 Y 尺度；如采用训练内标准化，保存参数并正确还原预测。

## 对 Harness 启动范围的调整

| 前期判断 | 本次数据带来的变化 | 当前优先级 |
|---|---|---|
| 没有正式训练包 | 用户已提供官方来源 ZIP，且全部任务/测试行匹配 | 记录来源和逐文件哈希，接入真实数据 |
| 可能需要为单个标注文件扩展派生划分接口 | 官方每任务已有独立 train/valid | 从启动必做范围移除通用划分接口；复用既有角色 |
| 训练 schema 未知 | 66 文件表头一致；Drug 是 SMILES，Y 是数值标签 | 编写固定加载映射，保留任务/划分/行号 |
| 可能要读取 3D 或预计算特征 | ZIP 仅有 SMILES 和标签；官方允许 SMILES 路线 | 第一版以实际输入为准，不以寻找 3D 文件为前置 |
| 需要演示全链路接口 | 仍需要，但真实数据已到，不必长期停留在合成 demo | 尽快过渡到真实分类、回归各一个任务的保存加载与预测 |
| 主要数据风险仍是假设 | 已看到重复标签、空 ID、跨任务划分交叉 | B 优先固定这些处理规则；C 的加载和 loss 必须遵循 |
| 大规模缓存/复制性能可能成问题 | CSV 原始内容仅约 5.43 MB | 不把缓存平台和 I/O 优化放到首日关键路径 |

仍保留：逐样本验证记录、统一评价、训练/预测语义兼容检查、目标环境验证、完整候选与复现。没有因为数据到位就假装容器、模型或标签科学解释已全部确认。

本次没有把原 `config/data_manifest.json` 改为 approved，也没有将原 `task_schema` 中未知单位强填为已知。实际接入时应以“原样官方 Y 的数值目标”和已知语义分别记录；不凭空猜解释，也不让与当前数值基线无关的解释问题阻塞全部开发。

## 四天安排的具体调整

总体保留 D1 真实运行、D2 完整候选、D3 增益、D4 交付，**首日减少准备工作，把时间转给真实实验与数据行为检查**。

| 时间 | A：Harness | B：数据与评价 | C：模型 |
|---|---|---|---|
| D1 上午 | 复用现有 train/validation 接口；把 66 文件、模板和哈希接入；确认目标运行环境 | 核定行身份、原样 Y、官方划分、重复记录与跨任务 loss 边界 | 对分类/回归各一个小任务实现并运行完整适配器 |
| D1 下午 | 验证 checkpoint 保存加载、逐样本评价及预测导出 | 检查真实模型输出与 Y 对齐、回归反变换、指标是否可比 | 在较大 CYP 任务上测吞吐和资源，再估算全量与重跑时间 |
| D2 | 全任务运行和候选检查 | 全任务指标、稀缺类别与重复标签影响审计 | 完成覆盖 22 任务的基线和完整预测 |
| D3 | 稳定运行、比较与版本记录 | 用相同验证口径支持选模，避免小样本分数波动造成误判 | 少量高价值实验，保留主备并按耗时安排最终训练 |
| D4 | 复现检查、候选文件及平台回执 | 独立复核样本对应和标签语义 | 固定配置推理/复跑与异常处理 |

B 与 C 现在可以直接基于真实文件并行，不需要等我们先造一个通用切分系统。数据量较小提高了快速基线的可行性，但还没有任何真实训练计时；不能据此承诺 GPU 时长或比赛分数，也不建议因此取消 D4 的交付缓冲。
